## Why

Live evaluation currently reuses the Research/Backtest range-computation model: every live-entry and open-trade request loads history from `earliest_committed_open_time_ms` through the target bar, then runs the full indicator/strategy pipeline over that entire range. On the current data depth this is hundreds of thousands of 5m bars per request and produces observed live latency of roughly 60-70 seconds. Live only ever needs the state near the target bar, so this full-history read is unnecessary work that scales with total accumulated market-data history rather than with strategy complexity. Fixing this now unblocks running the strategy on exchange within an acceptable latency budget without a large Engine rewrite.

## What Changes

- Add a pure, no-IO `PlanLiveHistoryStart` planner that computes a bounded history timestamp (`from_ms`) sufficient, under a set of configured indicator-convergence and strategy-semantic warm-up policies, to evaluate a given strategy spec's indicators and strategy components at a target bar, given a caller-supplied history anchor and base timeframe. For finite-window components this bound is exact; for recursive or stateful components it is a conservative policy validated by parity testing, not a mathematically minimal window.
- Add a generic `ResolveIndicatorHistoryRequirements` component that derives per-timeframe bar/lookback requirements from the already-built `IndicatorPlan` (finite lookback for RSI/ATR; recursive convergence warm-up for EMA and for the Wilder-smoothed ADX/DI cascade), keyed by `(timeframe, bars)`. A component with no independent requirement (e.g. `atr_distance`, which only scales an already-required upstream ATR) is recorded as an explicit zero-additional-warm-up entry, not silently omitted. An indicator kind with no registered policy SHALL fail closed rather than implicitly contribute zero history.
- Add an `ema_pullback`-owned `EmaPullbackLiveCalculationRequirements` component that derives semantic history requirements for every live-supported context/blocker/setup/trigger/risk/exit component audited for this change (`anchor_stack_width`, `untouched_anchor`, trigger reclaim, RSI/trend-strength blockers, exit `confirm_bars` windows). `ema_bounce_counter_setup` is a *conditional* requirement — present in the output only when the setup is actually configured in the spec — sized by an empirical V1 tier lookup keyed solely on the anchor EMA period (`anchor_stack.anchor.period`); fast/slow EMA periods do not affect tier selection (design.md Decision 12). An anchor period outside the empirically-measured envelope (> 1,000) with `ema_bounce_counter_setup` present fails closed rather than extrapolating or reusing the largest known tier. An unaudited/unrecognized component SHALL fail closed rather than implicitly contribute zero history.
- The planner combines these two sources additively, not by taking their maximum: `required_pre_anchor_span = indicator_warmup_span + strategy_semantic_span`, because strategy components consume already-computed indicator series (e.g. an RSI blocker reading 20 bars of RSI history needs RSI's own warm-up in front of that 20-bar window, not overlapping it) — see design.md Decision 4 for the worked example and why `max()` alone under-counts.
- `EvaluateLiveEntryProjection` and `EvaluateOpenTradeProjection` compute `history_anchor_open_time_ms` at the use-case level (`target` for live-entry; `min(source_plan_bar_open_time_ms, entry_bar_open_time_ms)` for open-trade) and pass it to `LoadLiveFeatureFrame`. `LoadLiveFeatureFrame` itself does not compute the anchor — it receives the already-resolved anchor, invokes the planner with it (the planner also needs `base_timeframe` to convert HTF requirements to base-timeframe span and to align the resulting window to a complete leading higher-timeframe resample bucket), and clamps the result against MDS bounds: `actual_from_ms = max(planned_from_ms, bounds.earliest_committed_open_time_ms)`, emitting a diagnostic when clamping truncates the requested warm-up. `to_ms` computation (`target_bar_open_time_ms + base_timeframe_duration`) is unchanged and remains owned by `LoadLiveFeatureFrame`, not the planner.
- Strategy-component semantic lookback (e.g. a blocker's `lookback` bar count) is measured on the bar axis the existing evaluator actually iterates over — for current `ema_pullback` components this is the base FeatureFrame axis (post-HTF-alignment), not the axis of whichever indicator's timeframe happens to feed the component — so a lookback count is never accidentally inflated by multiplying it against an unrelated indicator timeframe.
- Planner output (`PlannedHistoryStart`) carries `from_ms`, the winning indicator requirement, the winning strategy-semantic requirement, and the full requirement set for structured logging and diagnostics. The two winning-requirement fields are separate, explicitly-typed fields — not a single field whose source category must be inferred from a free-text `reason` string.
- Research/Backtest range computation (explicit caller-supplied `TimeRange`) is unchanged; the new planner is not invoked on that path.
- **BREAKING**: none — no Runtime-facing HTTP contract, request/response schema, or Research/Backtest semantics change. This is an internal live-calculation-path change only.

## Capabilities

### New Capabilities
- `live-calculation-window-planning`: pure, no-IO computation of a bounded, policy-sufficient live history start (`from_ms`) for a strategy spec, target bar, base timeframe, and history anchor, combining generic indicator warm-up requirements with strategy-specific (ema_pullback) event/lookback requirements additively, aligning to complete HTF resample buckets for every higher timeframe actually present in the indicator plan, and exposing the winning indicator and winning strategy-semantic requirements separately for diagnostics.

### Modified Capabilities
- `live-feature-frame-acquisition-v1`: the "Construct the exact half-open live range" requirement changes from `from_ms = earliest_committed_open_time_ms` to `from_ms = max(planned_from_ms, earliest_committed_open_time_ms)`, where `planned_from_ms` comes from the new planning capability; adds a diagnostic emission requirement when clamping truncates the planned warm-up window.

## Impact

- Affected code: `src/strategy_engine/strategies/application/load_live_feature_frame.py` (modify), `evaluate_live_entry_projection.py` / `evaluate_open_trade_projection.py` (tiny modify, to compute and pass `history_anchor_open_time_ms`), `service/wiring.py` (modify, wire new planner dependency).
- New code: `src/strategy_engine/strategies/live_calculation/` package (`contracts.py`, `indicator_requirements.py`, `plan_window.py`), `src/strategy_engine/strategies/ema_pullback/live_calculation_requirements.py`.
- Unaffected: indicator implementations (`ema.py`, `atr.py`, `rsi.py`, `adx_dmi.py`), `EvaluateIndicatorRange`, `RangeIndicatorEvaluator`, `BuildLiveStrategyFeaturePlan`, `evaluate_ema_pullback_frame`, Research/Backtest range evaluation, MDS API, Runtime → Engine HTTP contract.
- **Correctness principle: numeric parity, not categorical parity.** Every `PlannedFeature` output in the `IndicatorPlan`, plus the numeric/intermediate state strategy components compute on top of it, must match between full-history and bounded-window calculation over the downstream-consumed tail each component actually reads, not just the target bar. Finite-window values require exact equality; recursively-seeded values use a calibrated Decimal drift tolerance. A present-vs-absent value mismatch is always a hard failure, independent of any drift tolerance. Categorical/business outputs (`desired_entry`, side, `close_signal`, locked profile) are a lossy derivative of the numeric state and are not the acceptance gate. This change's calibration/validation tooling was disposable (used to select the EMA/ADX tolerances and the bounce tier policy below) and is not retained in the repository; the accepted values and policy are what carry forward.
- EMA/ADX convergence tolerance are fixed at `1e-4` from real-history calibration. `ema_bounce_counter_setup`'s history requirement is fixed as the anchor-EMA-period tier policy (design.md Decision 12). The bounded planner and its policies are implemented and unit-tested but not yet wired into the live loader — that wiring is Group 6, a separate, later phase.
- Known limitation carried forward: open-trade evaluation for long-lived positions still spans from warm-up-before-entry through the full trade lifecycle to target, so latency improvement is smaller there than for live-entry; documented as out of scope for this change.
