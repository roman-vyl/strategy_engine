## Context

See proposal.md - Why. Relevant current call flow (`load_live_feature_frame.py`):

```
ValidateLiveStrategySpec
  -> MDS.load_bounds()
  -> TimeRange(from_ms=bounds.earliest_committed_open_time_ms, to_ms=target+step)
  -> BuildLiveStrategyFeaturePlan
  -> EvaluateIndicatorRange -> MDS candles -> RangeIndicatorEvaluator
  -> EmaPullbackLiveEntryProjectionAdapter -> evaluate_ema_pullback_frame
```

`BuildLiveStrategyFeaturePlan` already decomposes the strategy spec into an `IndicatorPlan` (per-indicator `kind`, `timeframe`, `parameters`), so indicator warm-up requirements can be resolved from that existing structure without re-parsing the raw spec. Currently one live strategy family exists (`ema_pullback`).

## Goals / Non-Goals

**Goals:**
- Make live-entry calculation latency independent of total accumulated MDS history depth.
- Keep the change internal to Engine: no Runtime <-> Engine contract change, no Research/Backtest semantics change.
- Keep the existing downstream pipeline (`EvaluateIndicatorRange`, `RangeIndicatorEvaluator`, `evaluate_ema_pullback_frame`) untouched; only the computed `from_ms` changes.
- Make the planner pure and independently unit-testable (no MDS, no HTTP, no pandas).

**Non-Goals:**
- No incremental/stateful indicator computation, no persistent EMA/ADX state across requests.
- No change to how open-trade evaluation replays trade history; long-lived open trades remain bounded by entry/source-plan, not by target alone (documented limitation).
- No indicator-requirement registry/factory abstraction; with a single strategy family (`ema_pullback`), requirements are resolved via direct composition, not a plugin registry.
- No native multi-timeframe MDS reads (HTF still derived by resampling base-timeframe history) — a possible later stage, not part of this change.
- No trading-calendar/session-gap awareness in timeframe-duration conversion.

## Decisions

**1. Planner sits at the application boundary, immediately before `LoadLiveFeatureFrame`'s existing range construction — not inside indicator implementations, not inside MDS client code.**
Rationale: minimal change surface. The existing indicator implementations (`ema.py`, `atr.py`, `rsi.py`, `adx_dmi.py`) and the entire downstream evaluation pipeline are reused unchanged; only the `from_ms` fed into them changes. Alternative considered: attach a `required_history()` method to each indicator implementation directly. Rejected for V1 — more invasive, and the same information can be centralized in one resolver reading the existing `IndicatorPlan` output. Can be revisited if a second strategy family needs it.

**2. Two-tier requirement resolution: generic indicator requirements vs. strategy-specific event requirements, composed rather than unified.**
`ResolveIndicatorHistoryRequirements` operates only on `IndicatorPlan` (generic: EMA/RSI/ATR/ADX). `EmaPullbackLiveCalculationRequirements` lives inside the `ema_pullback` package and owns knowledge of strategy/event lookbacks (`anchor_stack_width`, `untouched_anchor`, triggers, blockers, `ema_bounce_counter_setup`). Rationale: the generic planner must not need to understand `ema_pullback`-specific concepts; this keeps the boundary clean for when a second strategy family is added, without introducing a registry now (see Non-Goals).

**2a. Dependency direction enforced via a `StrategyHistoryRequirements` Protocol, not just convention.** `PlanLiveHistoryStart` (`live_calculation/plan_window.py`) depends only on `StrategyHistoryRequirements` (`live_calculation/contracts.py`) — it does not import `strategy_engine.strategies.ema_pullback` and its `strategy_requirements` constructor argument is required, not defaulted. Which concrete strategy family backs the planner is left to whichever caller constructs it (Group 6's production wiring, or a test); no composition helper is created ahead of that real caller — introducing one prematurely would just be a different shape of the same coupling this decision removes. `tests/test_live_calculation_architecture.py` enforces the boundary as a regression test (`live_calculation/` must not import any concrete strategy-family package), not just as a docstring convention. No registry/plugin/factory framework was introduced — there is still exactly one live strategy family; this is purely a dependency-direction fix.

**3. Planner is pure: no MDS calls, no candle reads, no HTTP, no pandas.**
It takes a strategy spec, an `IndicatorPlan`, `base_timeframe`, and a caller-supplied `history_anchor_open_time_ms`, and returns `PlannedHistoryStart(from_ms, winning_indicator_requirement, winning_strategy_requirement, requirements)`. Two separate winning-requirement fields, not one: after Decision 4a's additive composition, `from_ms` is driven by two independent source categories (indicator warm-up span and strategy-semantic span) at once, so a single `winning_requirement` field cannot represent "which requirement is responsible" without a caller trying to reverse-engineer the source category from the free-text `reason` string — which this design explicitly avoids relying on. `base_timeframe` is required input, not derivable inside the planner: `IndicatorPlan` timeframes include the literal value `"base"`, and converting `(timeframe, bars)` into a duration requires knowing what `"base"` actually is (e.g. `5m`). This is not I/O — it is a value already available on the request (`request.market.base_timeframe`) — so it does not violate the pure/no-IO invariant. `LoadLiveFeatureFrame` remains the only place that talks to MDS and owns the final clamp against `bounds.earliest_committed_open_time_ms`. Rationale: keeps the planner trivially unit-testable and enforces a lint-level invariant (no MDS/pandas/http imports in `live_calculation/`) rather than a documentation-only convention.

**4. Planner owns only `from_ms`; `to_ms` computation stays in `LoadLiveFeatureFrame`.**
`to_ms = target_bar_open_time_ms + base_timeframe_duration` is unchanged existing logic and has nothing to do with warm-up sizing. Giving the planner a `from_ms`-only result type (`PlannedHistoryStart`, not a `from_ms`+`to_ms` window) avoids a second source of truth for `to_ms`.

**4a. Indicator warm-up and strategy-semantic history are composed additively, not combined via `max()`.**
Strategy components consume already-computed indicator series, not raw candles: an RSI(14) blocker with `lookback=20` reads the last 20 bars of an already-materialized RSI series, and RSI's own rolling(14) computation needs ~14 bars of warm-up in front of the frame before its first value is valid. A resolver that takes `max(rsi_requirement=15, blocker_requirement=20) = 20` bars gives the blocker a 20-bar frame whose first ~14 RSI values are still invalid — not the 20 valid historical RSI values the full-history reference path would have shown it. The same shape of problem applies to `anchor_stack_width_setup` (each `width` value itself depends on fast/anchor/slow EMA and ATR) and the trend-strength blocker (scans already-computed ADX/DI values). Rather than building a full per-component dependency graph (rejected as overkill for V1 — see Non-Goals), the planner sums two coarse spans:
```
required_pre_anchor_span = indicator_warmup_span + strategy_semantic_span
planned_from_ms = anchor - required_pre_anchor_span
```
where `indicator_warmup_span` is the maximum warm-up across all `IndicatorPlan` entries and `strategy_semantic_span` is the maximum semantic lookback across all resolved strategy components. This deliberately over-provisions history (a strategy component's lookback is stacked behind the full indicator warm-up even when that specific component doesn't consume that specific indicator) in exchange for guaranteed correctness of the consumer-sees-valid-upstream-values property, and for staying simple enough to reason about and test. `atr_distance` and similar upstream-scaling features contribute zero *additional* span of their own (they inherit ATR's) rather than being treated as an independent requirement.

**4b. Strategy-semantic bar counts are measured on the bar axis the existing evaluator actually iterates over, not on the axis of whichever indicator's timeframe happens to feed the component.**
For current `ema_pullback` evaluators, contexts/blockers/setups/triggers/exits run over the base FeatureFrame axis after HTF indicators have already been aligned onto it (existing `evaluate_ema_pullback_frame` behavior, unchanged by this design) — a component's configured `lookback` (e.g. an RSI blocker's `lookback=20`) counts 20 base-FeatureFrame bars, never `20 × <indicator timeframe>`, regardless of whether the RSI it reads happens to be computed on `1h`. Rule: *strategy-component bar counts SHALL use the bar axis on which the existing component implementation actually iterates; for current `ema_pullback` evaluators this is the base FeatureFrame axis unless a component explicitly defines another axis.* This matters because `strategy_semantic_span` (Decision 4a) is summed against `indicator_warmup_span`, which *is* per-indicator-timeframe before base-timeframe conversion (Decision 8) — conflating the two axes would silently multiply a strategy component's required span by an unrelated indicator's timeframe, over-provisioning history far beyond what Decision 4a's conservative-but-bounded intent calls for. No currently live-supported `ema_pullback` component defines a non-base semantic axis; if one is added later, its resolver entry must say so explicitly rather than defaulting to base.

**5. History anchor is computed once, at use-case level, never inside the planner and never inside `LoadLiveFeatureFrame`.**
`EvaluateLiveEntryProjection` computes and passes `history_anchor_open_time_ms = target_bar_open_time_ms`. `EvaluateOpenTradeProjection` computes and passes `min(source_plan_bar_open_time_ms, entry_bar_open_time_ms)`. `LoadLiveFeatureFrame` is purely a consumer of this value: it receives `history_anchor_open_time_ms` on its request, forwards it to the planner unchanged, and never derives or recomputes it. This avoids duplicating anchor-selection logic between the two use cases and `LoadLiveFeatureFrame`; the planner receives an already-resolved anchor and never branches on use case.

**6. Clamp against MDS bounds happens after planning, with a diagnostic on truncation, not a hard failure.**
`actual_from_ms = max(planned_from_ms, bounds.earliest_committed_open_time_ms)`. Rationale (reviewed and accepted): the full-history reference path has exactly the same physical floor — if MDS doesn't have the history, no calculation path could use it. A hard-fail here would reject requests the current system already serves. The cost is made visible instead: emit a structured diagnostic when truncation occurs, so silent degradation cannot hide inside an aggregate result.

**7. Recursive-indicator warm-up (EMA, and the Wilder-smoothed ADX/DI cascade) is a fixed convergence-tolerance policy, computed once, not measured per-request.**
Engine's EMA is `.ewm(span=period, adjust=False).mean()`, i.e. `y[n] = alpha*x[n] + (1-alpha)*y[n-1]` with `alpha = 2/(period+1)`. The influence of an arbitrary seed value decays as `(1-alpha)^n`, **not** `alpha^n` — the earlier draft of this design had the decay base inverted, which for EMA200 at a `1e-6` tolerance is the difference between ~3 bars (wrong) and ~1382 bars (correct: solve `(1-alpha)^n < tolerance`). ADX is a *separate* recursive case, not folded into the EMA formula: `compute_adx_dmi` runs Wilder's RMA (`out[i] = (previous*(period-1) + current) / period`, decay base `(period-1)/period`) first on TR/+DM/-DM, then a second RMA pass on DX to produce ADX — a two-stage recursive cascade with its own convergence-tolerance derivation, computed and validated independently from the EMA policy, not reused from it. RSI and ATR remain finite-window (a bar count fully bounds their history dependence; no recursive seed-influence term). Convergence tolerance and any semantic-lookback constants (see Open Questions) are not per-request configurable in V1; they were fixed via real-history numeric-parity calibration and can be tightened later if production monitoring says otherwise.

**8. Higher-timeframe requirements convert to base-timeframe span via fixed candle duration, then the resulting `from_ms` is rolled back to the start of the corresponding HTF resample bucket, using the same fixed-duration UTC alignment semantics as the existing pandas resample — for every higher timeframe actually present in the indicator plan, not only the timeframe of the single largest requirement.**
Matches current HTF construction (`frame.resample(timeframe, label="left", closed="left")` on base-timeframe history, which buckets on fixed-duration UTC boundaries — e.g. `4h` buckets start at `00:00, 04:00, 08:00, ...` UTC). Precise rule: for a `4h` requirement with a computed candidate `from_ms` of `06:35`, the aligned `from_ms` is rolled back to `04:00` — the start of the `4h` bucket containing `06:35` — using the identical boundary semantics pandas resample already applies, not an independently invented alignment rule. A `from_ms` left at `06:35` would make the existing resample pipeline emit an incomplete leading `4h` candle backed only by `06:35→08:00` of base data instead of the full `04:00→08:00` window the full-history reference path would have produced; that incomplete candle would then seed EMA/ADX on the bounded path with a value the reference path never had, defeating the goal before parity testing even runs. Because indicator warm-up spans are combined via `max()` within the indicator source category (Decision 4a) before being summed with `strategy_semantic_span`, the single earliest `from_ms` candidate is not automatically aligned for every HTF the spec uses — e.g. a spec with both `1h` RSI and `4h` EMA200 has two independent bucket-alignment constraints, and satisfying the `4h` one does not guarantee the `1h` one is satisfied for a `from_ms` that happens to land elsewhere. The planner therefore applies bucket-alignment as a final pass over every distinct higher timeframe present in the indicator plan, rolling `from_ms` back further as needed until it sits on a bucket boundary for all of them simultaneously (still no I/O — pure calendar arithmetic against fixed durations). The fixed-duration conversion itself is explicitly not calendar-aware beyond this bucket-alignment; acceptable because the only live venue in scope is Bybit crypto (24/7). Flagged in code with a comment, not just in this document, since a future multi-venue Engine would silently violate this assumption otherwise.

**9. `PlannedHistoryStart` carries the winning indicator requirement, the winning strategy-semantic requirement, and the full requirement set for diagnostics.**
Two distinct fields, not one (see Decision 3): after additive composition, `from_ms` is jointly determined by the largest indicator-side span and the largest strategy-side span, and both need to be independently visible without requiring a caller to parse a `reason` string to figure out which category a given `HistoryRequirement` belongs to. Prevents needing to re-derive "why was this window chosen" purely from operational logs.

**10. Unrecognized indicator kinds or strategy components fail closed rather than silently contributing zero required history.**
The resolver's mapping from indicator/component kind to a history policy is an explicit, exhaustive `match`/lookup; a kind with no registered policy raises rather than being treated as requiring no warm-up. Rationale: a resolver that implicitly defaults to zero history for anything it doesn't recognize is a silent correctness regression waiting for the next new indicator or strategy component to be added to `IndicatorPlan`/`ema_pullback` without a matching resolver entry — it would pass all existing tests and simply under-provision history for the new component. This is a plain `else: raise`, not a registry/plugin system (see Non-Goals), so it doesn't reintroduce the complexity avoided by Decision 2.

**11. `live-calculation-window-planning`'s language is "bounded, policy-sufficient" history, not "minimal, correct" history.**
For finite-window components (RSI, ATR, fixed-lookback strategy components) the bound is exact. For recursive or semantically stateful components (EMA, ADX/DI, and especially `ema_bounce_counter_setup`, whose `completed_count` state is not bounded by any fixed lookback — a trend episode may have started arbitrarily far in the past) there is no finite window that is provably "the minimum required for identical output" without persistent state (a Non-Goal here). The spec and code therefore describe this as a conservative empirical policy, not a claim of mathematical minimality or guaranteed exact correctness. If a bounded policy proves insufficient for a given component in production, that component becomes a candidate for a later incremental/stateful stage, not a reason to weaken this change's honesty about what it delivers.

**12. `ema_bounce_counter_setup`'s history requirement is a conditional, anchor-EMA-period-only tier lookup — no persistent state, no special planner branch, fast/slow EMA excluded from tier selection.**
V1 explicitly does not introduce persistent bounce state, incremental restoration, a dedicated Runtime state channel, or a special bounce calculation path (all remain Non-Goals). Instead `ema_bounce_counter_setup` stays exactly what every other strategy component already is in this design: an ordinary, *conditional* entry in `EmaPullbackLiveCalculationRequirements`'s output — present only when the setup is actually configured in the spec, absent otherwise, and combined into `strategy_semantic_span` (Decision 4a) via the same `max()`-then-sum composition every other strategy requirement already uses. `PlanLiveHistoryStart`'s composition formula is untouched.

Sizing policy: a `_BounceHistoryTier(max_anchor_period, history_bars)` lookup keyed **solely** on `anchor_stack.anchor.period` — the fast and slow EMA periods do not participate in tier selection at all, even though they fully participate in the real `ema_pullback` EMA stack and `trend_active` computation (untouched). Rationale: a tier keyed on the exact `(fast, anchor, slow)` tuple is brittle — a spec with `anchor=199` instead of a measured `anchor=200` would become "unrecognized" for no principled reason, since the fast/slow periods are largely independent stylistic choices while the anchor period is what actually sets the scale of the EMA-ordering condition `trend_active` tests. The anchor period alone is treated as a stable-enough classifier for V1; this is an explicit simplification, not an oversight.

V1 tiers, empirically derived from real BTCUSDT.P/ETHUSDT.P full-history `trend_active` episode-length measurement across three production-family anchor-stack sizes:

| anchor EMA period | observed max episode | policy `history_bars` |
|---|---|---|
| ≤ 200 | 1,832 | 2,500 |
| 201-500 | 4,736 | 6,000 |
| 501-1,000 | 11,000 | 15,000 |
| > 1,000, bounce present | no empirical data at this scale | fail closed |

This is an empirical V1 policy informed by measurement on the only three anchor-stack families actually measured — **not** a mathematically derived upper bound, the same honesty framing as Decision 11 for EMA/ADX. Fail-closed above anchor=1,000 (only when `ema_bounce_counter_setup` is actually present — a spec with a large anchor and no bounce setup is unaffected) follows Decision 10's existing principle: rather than extrapolating a formula, defaulting to the largest known tier, or reusing an unmeasured placeholder, an anchor period outside the measured envelope is treated the same as any other unrecognized case — explicit failure, not silent under-provisioning. The calibration/validation tooling used to derive and check this table was disposable research infrastructure and is not retained in the repository; the table above is the artifact that carries forward.

## Risks / Trade-offs

- **[Risk] Insufficient warm-up tolerance silently changes live decisions in a way backtest never exercises.** -> Mitigation: the acceptance principle for this change is numeric parity — every `IndicatorPlan` output and every strategy-component numeric/intermediate value it feeds must match between full-history and bounded-window calculation (not just `desired_entry`/`close_signal`, which are lossy booleans that can coincidentally agree despite underlying drift) — verified via real-history calibration before the fixed tolerances below were adopted.
- **[Risk] Aggregation bug in requirement resolution (e.g., only the top-level requirement considered, not the max across a dependency chain through HTF resample) understates required history.** -> Mitigation: `ResolveIndicatorHistoryRequirements`/`EmaPullbackLiveCalculationRequirements` are unit-tested independently against known indicator formulas and known strategy-component lookbacks.
- **[Risk] Open-trade evaluation for long-lived positions sees little to no latency improvement**, since its anchor is `min(source_plan, entry)`, not target, and can predate target by weeks or months. -> Mitigation: explicitly out of scope for this change (see proposal Impact); live-entry and open-trade latency are tracked as separate SLA/perf metrics so an open-trade regression cannot be masked by live-entry improvement.
- **[Trade-off] No hard-fail on truncated warm-up.** -> Accepted because it matches existing reference-path behavior at the same physical data boundary; a structured diagnostic on truncation substitutes for hard rejection.
- **[Trade-off] Fixed-duration timeframe conversion ignores trading-session gaps.** -> Acceptable for the current single-venue (Bybit, 24/7 crypto) deployment target; would need revisiting before supporting a venue with trading-session gaps.
- **[Risk] An HTF-consuming component seeded from an incomplete leading resample bucket produces a value the full-history reference path never had, independent of warm-up length; a spec using multiple higher timeframes at once could satisfy bucket-alignment for one and not the others.** -> Mitigation: Decision 8's bucket-alignment step applied per distinct higher timeframe present in the indicator plan (not only the timeframe of the single largest requirement), plus dedicated tests for targets sitting inside a `1h`/`4h` bucket, a `from` candidate that does not naturally land on a bucket boundary, and a spec using multiple HTFs simultaneously.
- **[Risk] Strategy-semantic lookback accidentally measured on an indicator's timeframe axis instead of the base FeatureFrame axis it's actually evaluated on, silently multiplying the required span.** -> Mitigation: Decision 4b's explicit axis rule, plus a dedicated test asserting a strategy component's resolved span does not scale with an unrelated indicator's timeframe.
- **[Risk] `max()`-based combination of indicator and strategy-component requirements under-counts because strategy components consume already-computed indicator series, not raw candles.** -> Mitigation: Decision 4a's additive composition (`indicator_warmup_span + strategy_semantic_span`), with a dedicated unit test for a composite case (e.g. RSI14 blocker with lookback=20) asserting the consumer's window contains no invalid upstream values.
- **[Risk] `ema_bounce_counter_setup`'s trend-episode memory has no fixed bound, so a bounded semantic warm-up is an approximation with no correctness proof.** -> Mitigation: Decision 12's anchor-EMA-period tier policy, empirically derived from real BTCUSDT.P/ETHUSDT.P `trend_active` episode-length distributions across three production-family anchor-stack sizes; explicit fail-closed beyond the measured envelope (anchor > 1,000); explicit escalation path to a future stateful stage if production data ever shows the policy is insufficient, rather than silently widening a tier.

## Migration Plan

A single non-contradicting sequence — nothing here is wired into the live loader until step D:

1. **(A)** Land `live_calculation/` package (`contracts.py`, `indicator_requirements.py`, `plan_window.py`) and `ema_pullback/live_calculation_requirements.py` — contracts, resolvers, and the pure planner — unused by any call path yet. **Done.**
2. **(B)** Unit test each piece independently: indicator requirement math, strategy-component requirement math, additive composition, timeframe conversion, HTF bucket alignment, fail-closed behavior. **Done.**
3. **(C)** Calibrate the policy constants (EMA convergence tolerance, ADX/DI convergence tolerance, `ema_bounce_counter_setup` anchor-period tiers) against real historical data under the numeric-parity acceptance principle, and fix them as concrete values in code. **Done** — the calibration/validation tooling used for this was disposable and is not retained in the repository; the accepted values (Decisions 7/12) are what carry forward.
4. **(D)** Modify `EvaluateLiveEntryProjection` and `EvaluateOpenTradeProjection` to compute and pass `history_anchor_open_time_ms`; modify `LoadLiveFeatureFrame` to accept that anchor, invoke the planner, and compute the planned-and-clamped `from_ms` instead of `earliest_committed_open_time_ms`; wire the planner and its dependencies (including the concrete `ema_pullback` strategy-requirements implementation) at the composition boundary. No feature flag needed — no external contract changes, and Research/Backtest paths are unaffected since they never call this planner. **Group 6 — not started.**
5. **(E)** Integration, regression, and performance tests against the now-wired live path: Research/Backtest isolation, bounded-range reads, open-trade anchor-before-target reads, MDS-bounds clamping, fail-closed behavior end-to-end, and live-entry/open-trade latency measured separately, before and after.
6. **(F)** Rollout: review results, enable the bounded live path in production, document the open-trade long-position latency limitation.
7. Rollback: revert `LoadLiveFeatureFrame` to the prior `from_ms = earliest_committed_open_time_ms` construction; the new package can remain unused without further changes since nothing else depends on it.

## Open Questions

- ~~**EMA/ADX convergence tolerance value(s).**~~ **Resolved.** Fixed at `1e-4` for both `_CALIBRATED_EMA_CONVERGENCE_TOLERANCE` and `_CALIBRATED_ADX_DMI_CONVERGENCE_TOLERANCE`, chosen via real-history numeric-parity calibration with comfortable tested headroom below the loosest value that also showed zero mismatches.
- ~~**`ema_bounce_counter_setup` conservative semantic warm-up horizon.**~~ **Resolved (Decision 12).** Sized by the anchor-EMA-period tier policy (`_BOUNCE_HISTORY_TIERS` in `ema_pullback/live_calculation_requirements.py`), not a flat universal horizon.
- **Non-trivial numeric-drift threshold.** No sweep to date has produced measurable non-zero drift to calibrate a hard threshold against (every measured field matched exactly or with negligible relative drift at the chosen tolerances). Remains theoretical, carried forward as residual risk for production monitoring rather than blocking this change.
